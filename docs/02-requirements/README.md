## 0. 먼저 보는 핵심 요구사항 (1분 요약)

**한 문장:** 국민이 의심 문자를 입력하고 *현재 상황*을 선택하면, K-SAFE는 개인정보를 가린 뒤 위험 근거와 우선해야 할 안전행동을 안내한다.

**해커톤 주제 연결:**
- **AI 기반 추천 서비스:** 사용자의 상태(송금 전 / 이미 송금 / 앱 설치 / 기타)를 반영하여 안전행동의 순서와 문구를 바꾼다. 추가 개인정보 수집 없이 상황만 선택한다.
- **AI 기반 정보보호 서비스:** 스미싱·금융기관 사칭 위험 신호를 규칙+AI로 분석하고, 민감정보 최소처리·불확실성 고지를 적용한다.

**MVP(최소기능제품) 완성 정의:**
가상 의심 메시지를 붙여넣기 → 마스킹 → 분석 → 근거 표시 → 상황별 행동 안내 → 공식 신고·확인 방법을 보여주는 **하나의 작동하는 웹 흐름**. '이미 송금함'을 선택하면 AI를 기다리지 않고 즉시 긴급 대응을 안내한다.

**범위 밖:** 실계좌 조회/지급정지, 정부·은행 시스템 직접 연동, 실시간 통화 감청·녹음, 악성 URL 자동 접속, 외부 개인정보 유출 DB 검색, 실제 금융사기 사실의 법적 확정.

## 1. 사용자·범위·용어

### 1-1. 사용자 유형

| ID | 사용자 | 성공한 경험 |
|---|---|---|
| U-01 | 의심 문자를 받은 일반 국민 | 송금/설치를 멈추고 위험 근거를 읽고 공식 채널로 직접 확인 |
| U-02 | 이미 돈을 이체한 국민 | 별도 AI 분석 전이라도 우선 연락 경로를 즉시 파악 |
| U-03 | 의심 앱을 설치한 국민 | 기기·금융정보 보호를 위한 기본 순서와 상담 경로를 확인 |
| U-04 | 디지털 사용이 익숙하지 않은 국민 | 짧은 문장, 충분한 대비, 쉬운 용어로 안내를 이해 |

### 1-2. 용어

- **FR (Functional Requirement, 기능 요구사항):** 사용자가 실제 수행할 수 있어야 하는 기능
- **NFR (Non-Functional Requirement, 비기능 요구사항):** 속도·접근성·안정성 등 품질 기준
- **SR (Security Requirement, 보안 요구사항):** 개인정보·비밀키·위험 입력을 안전하게 다루기 위한 조건
- **AC (Acceptance Criteria, 수용 기준):** 요구사항 완료를 PASS/FAIL로 판단하는 구체 조건
- **TC (Test Case, 시험 사례):** 수용 기준을 확인하는 입력과 예상 결과
- **MVP (Minimum Viable Product, 최소기능제품):** 해커톤에서 실제 시연할 최소 기능
- **LLM (Large Language Model, 대형언어모델):** 자연어의 위험 맥락을 분석·설명하는 보조 모델
- **Fallback(대체 동작):** AI가 실패해도 안전한 규칙 기반 안내를 보여주는 동작

## 2. 핵심 사용자 흐름

\`\`\`mermaid
flowchart TD
    A["의심 문자 입력 또는 예시 선택"] --> B["현재 상황 선택"]
    B --> C{"이미 송금했는가?"}
    C -->|예| D["즉시 긴급 연락 안내 (AI 응답 대기 없음)"]
    C -->|아니요| E["입력값 확인"]
    D --> E
    E --> F["민감정보 가림"]
    F --> G["고정 규칙으로 위험 신호 추출"]
    G --> H["AI 맥락 설명 (가능할 때만)"]
    H --> I["위험 근거 + 불확실성 표시"]
    I --> J["상황별 다음 안전행동 추천"]
    J --> K["공식 확인·신고 경로 안내"]
\`\`\`

※ '이미 송금' 안내는 네트워크·LLM을 거치지 않고 즉시 보여준다. AI 설명이 실패하거나 지연되면 규칙 기반 결과로 대체한다.

## 3. 기능 요구사항 (FR)

| ID | 우선순위 | 기능 | 수용 기준(AC) | 시험 ID |
|---|---|---|---|---|
| **FR-01** | Must | 메시지 입력 또는 사전 제작 합성 예시 선택 | 빈 입력에는 분석을 수행하지 않으며 한국어 오류 표시. 입력은 2,000자 이하만 허용(초과 시 안내) | TC-01 |
| **FR-02** | Must | 사용자 상황 선택 | '송금 전·이미 송금함·앱 설치함·잘 모르겠음' 중 1개를 선택할 수 있고 추천 결과에 반영 | TC-02 |
| **FR-03** | Must | 개인정보 탐지·가림 | 합성 전화번호·계좌번호·이메일을 외부 AI 전송 이전에 가림. 가림 전후 예시로 검증. 실데이터는 쓰지 않음 | TC-03 |
| **FR-04** | Must | 의심 신호 탐지 | 합성 메시지의 '선입금 요구·외부 앱 설치·긴급조치 유도·기관 사칭' 중 감지 근거를 표시 | TC-04 |
| **FR-05** | Must | AI 설명 | 가림 처리된 메시지만 AI에 전달해 근거를 쉬운 한국어로 요약. AI 실패 시 규칙 기반 결과로 대체하며 성공으로 위장하지 않음 | TC-05 |
| **FR-06** | Must | 불확실성 안내 | '위험 징후/추가 확인 필요/명확한 징후 없음' 등 판단의 한계를 표시하고 **안전 확정** 표현 금지 | TC-06 |
| **FR-07** | Must | 상황별 안전행동 추천 | 동일한 입력에서 상황 선택을 바꾸면 권고 내용·우선순위가 변화. '이미 송금함'은 분석 요청 전 즉시 112/금융회사 연락을 최상단에 표시 | TC-07 |
| **FR-08** | Must | 공식 신고·확인 경로 | 직접 전화해 확인하도록 안내하고, 긴급 112 및 금융회사 공식 연락 방법을 표시. 클릭 가능 링크는 승인된 정적 주소만 허용 | TC-08 |
| **FR-09** | Should | 결과 이해·접근성 | 제목·위험근거·다음행동을 시각적으로 구분, 키보드로 조작 가능하며 쉬운 한국어 유지 | TC-09 |
| **FR-10** | Should | 합성 예시 시연 | 위험 1종·정상 1종·모호 1종을 버튼으로 불러오고 화면에서 2~3분 내 시연 가능 | TC-10 |

*Must = 24시간 내 반드시 구현, Should = 시간이 허용되면 구현. Must라도 품질·보안 게이트 미통과 시 제출 준비 완료로 간주하지 않는다.*

### 3-1. 보조 판정 로직

- **고위험 규칙 신호**와 **LLM 설명**은 별개: AI가 규칙 신호를 임의로 지우거나 피해자에게 송금을 권하지 못하도록 한다.
- 위험 수준은 안전 여부를 보증하는 점수가 아니라 **위험 신호 안내**다. 합성 데이터 검증 전 확률이나 탐지율을 수치로 표시하지 않는다.
- '이미 송금' 상태는 문자 내용과 관계없이 긴급 안내를 우선한다.
- 공공기관/금융기관을 사칭한 문자 안의 명령은 **분석할 데이터**일 뿐, 시스템 명령으로 실행하지 않는다.

## 4. 비기능 요구사항 (NFR)

| ID | 영역 | 수용 기준 | 시험 ID |
|---|---|---|---|
| **NFR-01** | 응답성 | 입력·상황 전환 후 즉시 화면 반응. '이미 송금' 긴급 안내는 외부 AI 호출 없이 렌더링 | TC-11 |
| **NFR-02** | AI 지연·장애 | AI 요청은 타임아웃을 설정(개발 시 수치 확정), 실패 시 경고와 규칙 기반 안내 표시 | TC-12 |
| **NFR-03** | 사용성 | 데스크톱/모바일 화면에 핵심 문구가 잘리지 않음. 화면 상태(대기·분석중·성공·오류)를 구분 | TC-13 |
| **NFR-04** | 접근성 | 버튼·입력폼에 이름(label) 제공, 키보드만으로 주요 시나리오 실행, 색상 외 텍스트로도 위험 표시 | TC-14 |
| **NFR-05** | 배포 | 심사위원이 HTTPS 공개 URL에 접속하여 예시 데이터를 실행할 수 있음 | TC-15 |
| **NFR-06** | 재현성 | 저장소 README에 실행·환경 설정·시험 명령을 기록해 다른 개발자가 재현 가능 | TC-16 |
| **NFR-07** | 비용·운영 | 사전 지정한 AI 사용량 제한 및 요청 제한을 두고, 불필요한 로그·비용 발생을 회피 | TC-17 |

## 5. 보안·개인정보 요구사항 (SR)

| ID | 위험 | 필수 통제와 수용 기준 | 시험 ID |
|---|---|---|---|
| **SR-01** | 민감정보 외부 전송 | AI API 요청 직전 서버 측에서도 개인정보 가림을 검사. **정규식만으로 모든 개인정보를 완벽히 탐지한다고 주장하지 않음.** 실제 데이터 입력을 지양하도록 고지 | TS-01 |
| **SR-02** | API 비밀키 유출 | API 키는 서버 환경변수로만 보관. \`.env\`·비밀키·로그의 저장소 커밋 금지. 클라이언트 응답에 비밀키 미포함 | TS-02 |
| **SR-03** | 프롬프트 인젝션 | 사용자가 붙여넣은 문구는 지시사항이 아닌 비신뢰 데이터. '이전 지침 무시'를 포함해도 우선 안전 규칙·안내 유지 | TS-03 |
| **SR-04** | 악성 URL/SSRF | 사용자가 넣은 외부 URL은 렌더링 시 클릭 가능한 자동 링크로 만들지 않고 **서버에서 자동 방문하지 않음**. 허용된 공식 링크만 별도 제공 | TS-04 |
| **SR-05** | 로그·보관 | 원본 메시지·민감정보·AI 전달 원문을 로그·분석 서비스에 저장하지 않도록 설계. 해커톤에서는 영구 저장소 불필요 | TS-05 |
| **SR-06** | 과도한 요청 | 길이·형식 검증, API 호출 횟수 제한 등 기본 오남용 방어 제공 | TS-06 |
| **SR-07** | 잘못된 금융행동 | AI가 계좌이체·앱 설치·계정정보 입력·자체 지급정지 완료를 권하거나 실행하지 않음. 실제 피해는 공식기관에 즉시 연락하도록 안내 | TS-07 |

> **보안 제약:** 실제 사용자의 금융정보로 서비스 성능을 검증하지 않는다. 합성 테스트에 통과하더라도 현실 피해 탐지의 정확도나 안전성이 입증된 것으로 말하지 않는다.

## 6. 데이터·입출력 계약 (초안)

코드를 구현하기 전 합의할 **데이터 계약(Data Contract)**이며, 실제 API가 존재하거나 동작한다는 뜻은 아니다.

**입력 예시 — 모두 합성 자료**

\`\`\`json
{
  "message": "저금리 전환을 위해 먼저 상환금을 보내고 전용 앱을 설치하세요.",
  "situation": "before_transfer"
}
\`\`\`

**상황 열거형:** \`before_transfer\`(송금 전), \`already_transferred\`(이미 송금), \`installed_app\`(앱 설치), \`unsure\`(잘 모르겠음).

**출력 예시 — 예상 구조**

\`\`\`json
{
  "risk_level": "warning",
  "signals": ["upfront_payment", "unverified_app_install"],
  "reasons": ["선입금 요구", "출처 불분명한 앱 설치 유도"],
  "uncertainty_notice": "이 결과만으로 사기 여부를 확정할 수 없습니다.",
  "recommended_actions": [
    "송금 및 앱 설치를 중단하세요.",
    "금융회사 공식 대표번호로 직접 사실을 확인하세요."
  ],
  "source": "rules_with_ai_explanation",
  "analysis_status": "completed"
}
\`\`\`

- 위험 수준 후보: \`warning\`, \`review\`, \`no_clear_signal\` (마지막은 '**안전 확인**'을 뜻하지 않음).
- 출처 후보: \`rules_with_ai_explanation\`, \`rules_fallback\`.
- AI 실패 시 \`analysis_status\`를 오류/대체 상태로 정확히 표시한다.
- 우선 긴급 연락 안내는 **클라이언트 화면에서 즉시 제공**하고, 응답 데이터에 의존하지 않는다.
- 원문 메시지와 개인정보를 결과 JSON에 되돌려 보내지 않는 것을 원칙으로 한다.

## 7. 24시간 우선순위·작업 배분

| 순서 | 범위 | 담당 개발 초점 | 완료를 보여줄 증거 |
|---|---|---|---|
| 1 | Must | 화면 입력·상황 선택·긴급 안내 | 사용자 동작 영상 또는 직접 시연 |
| 2 | Must | 개인정보 가림 + 규칙 탐지 | 합성 테스트 TC-03·TC-04 |
| 3 | Must | AI 설명 + 오류 대체 동작 | TC-05·TC-12 |
| 4 | Must | 근거·안전행동·공식 확인 경로 | TC-06~08 |
| 5 | Must | 보안 점검·반응형 화면·공개 배포 | TS 시험 + TC-15 |
| 6 | Should | 접근성·합성 예시·시연 품질 | TC-09·TC-10·TC-14 |

시간이 부족하면 Should부터 제외한다. **긴급 안내, 비밀키 보호, 합성 데이터, 공식 확인 경로, 허위 확신 금지는 제외할 수 없다.**

| J-05 개인정보·보안 | FR-03, SR-01~07 | 마스킹·비밀키·인젝션·URL 시험 |

## 9. 검증 시험 시나리오 (사전 설계, 아직 미실행)

| TC-01 | 빈 메시지 / 2,001자 입력 | AI 호출 없이 입력 오류 표시 |

| TC-15 | 실제 HTTPS 배포 URL 방문 | 서비스 접속·핵심 흐름 실행 |

**합성 데이터 목표:** 최소 30개 사례(위험, 정상, 경계)를 05단계에서 정의·실행하고, 오경보·누락·권고 적절성을 측정한다. 목표치와 **실제 측정치**를 혼동하지 않는다.

## 11. 03단계 설계에 넘기는 결정 사항

1. 입력 문자 처리: UI에서 먼저 안내·가림, 서버에서도 재검사(중복 방어).
2. 긴급 상황 안내: 네트워크 의존 없이 즉시 노출.
3. 위험 판단 구조: 규칙 신호 고정 + LLM 설명(보조), 위험 점수 확정 선언 금지.
4. UI 레이아웃: '위험 근거 → 지금 할 일 → 공식 확인'의 시각적 우선순위.
5. 테스트 설계: 합성 사례 30개 이상, 정상·위험·경계 유형과 개인정보 공격문 포함.
6. 배포 설계: HTTPS, 비밀키 서버 보관, 개인정보 원문 로그 미수집, 요청 제한.
7. 대회 조건 미확정: 참가할 해커톤 공식 공고 확인 후 평가 가중치·필수 제출물 조정.
